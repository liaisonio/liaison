# Agent history capacity and recovery baseline

## Scope and isolation

This is a local DAO baseline, not a production capacity claim or an HTTP load
test. All database records are synthetic and stored in an automatically removed
temporary SQLite database. No live database was copied, queried for load, or
modified. Real-session checks used a separate temporary access and project;
the test access and session were deleted afterward.

## SQLite setup

- Platform: macOS ARM64, 10 logical CPUs, Go 1.26.8.
- Production-equivalent configuration: WAL, synchronous NORMAL, 2 MiB page
  cache, memory temp store, 256 MiB mmap limit, normal locking, one open/idle
  connection, one-hour connection lifetime.
- 500 current session snapshots and 2,000 archived round pages, each with a
  synthetic 16 KiB payload (about 39 MiB before indexes and SQLite overhead).
- 1,000 operations per worker; concurrency 1, 8 and 32. Each worker performs
  75% 20-page history reads, 20% revision-increasing snapshot saves, and 5%
  50-session list reads. Each writer owns its own session.
- Setup excluded from timings. One measured run without race instrumentation,
  then the same workload with race detection for correctness. These are short,
  warm-cache closed-loop measurements, not a soak test or a saturation curve.

| 8 | 8,000 | 5,276 | 3.740 / 5.655 ms | 6.586 / 8.497 ms | 3.820 / 5.692 ms | 0 |
| 32 | 32,000 | 5,621 | 15.713 / 24.003 ms | 25.177 / 35.605 ms | 15.402 / 24.031 ms | 0 |

Pool wait counts were 0 / 8,358 / 33,593. Cumulative waits were 0 / 10.48 /
173.59 seconds; these are summed across workers, not elapsed wall time. The
single-connection pool serializes database work: throughput stays roughly flat
while concurrent-request tail latency rises. Lists are more expensive because
they load up to 50 snapshot payloads in addition to counting rows.

Race-instrumented verification also completed all 41,000 operations with zero
errors and no race reports. Its timing is not compared to the uninstrumented
baseline. Tests assert query bounds, final saved revisions and payloads, and
SQLite quick-check integrity, not hardware-dependent timing.

## Real session and latency checks

- Two independent browser contexts received the same real native response.
- Browser offline/online plus reload retained history and full-page view.
- Explicit stop retained server history; resume reopened the same native
  thread, with the prior message still present.
- Separate real native adapter tests exercised a plan-mode question/answer,
  command approval accept, and command approval decline. Accept created only
  the synthetic marker in the temporary project; decline left it absent. Both
  continued to a completed response and resumed the same thread after restart.
  The approval tests are adapter-level, not a claim of live browser approval
  coverage; browser dialogs have separate deterministic UI regression coverage.
- Desktop and mobile screenshots were inspected; no document-width overflow
  or browser runtime exceptions were observed. The narrow-screen session list
  uses its existing overlay behavior.
- The deployed HTML and all 106 referenced local build assets matched by hash;
  no Manager or Edge restart was needed for the frontend deployment.

One successful end-to-end sample measured: native session start through the
service 1,503 ms, snapshot round trips 31–91 ms, browser send acknowledgement
123 ms, visible assistant response in both browsers 10,975 ms, stop 104 ms,
resume 463 ms. These are individual samples, not percentiles.

A separate direct local app-server sample, with no Liaison transport, measured
startup/initialization 92 ms, turn acknowledgement 36 ms, first assistant text
9,998 ms, completion 10,185 ms. It used the installed default model and a short
no-tools prompt. The live browser test used a different short no-tools prompt;
the two measurements must not be subtracted to estimate network overhead.

The evidence places most of this sample's wait after app-server acknowledgement,
not in browser delivery or startup. It does **not** distinguish Codex internal
processing from provider/network/model latency. Native first text is not the
provider's first token. No private model reasoning or credentials were recorded.

## Conclusions and limits

- No SQLite lock errors or correctness failures appeared at this tested scale.
  This does not establish a user/session capacity limit or an online SLO.
- Retain bounded history pagination and payload limits. Track DB pool wait,
  database/WAL size, disk headroom, and API P95/P99 before changing storage.
- Do not increase SQLite connection count blindly: concurrent writers still
  serialize and may introduce lock failures. A metadata-only session list is
  a candidate if measured live list costs justify a schema/design change.
- Next capacity qualification should use production-equivalent hardware,
  larger varied payloads, cold-cache and sustained load, encrypted API paths,
  background sync, and unrelated service traffic. Reserve headroom against an
  explicit SLO; this short local run does not measure a safe production ceiling.
- Further model-latency attribution needs provider-side timing or native
  instrumentation, not a faster polling loop or speculative timeout changes.

## Reproduction

```sh
LIAISON_TEST_HISTORY_CAPACITY=1 go test ./pkg/liaison/repo/dao \
  -run '^TestAgentHistoryCapacity$' -count=1 -v
LIAISON_TEST_HISTORY_CAPACITY=1 go test -race ./pkg/liaison/repo/dao \
  -run '^TestAgentHistoryCapacity$' -count=1 -v
```

Native checks are opt-in, start only owned app-server processes, and may incur a
small model request. They require an existing authenticated native installation.

```sh
LIAISON_TEST_CODEX_HANDSHAKE=1 LIAISON_TEST_CODEX_TURN=1 \
  go test -race ./pkg/edge/agent/adapters/codex \
  -run '^TestLocalHandshake$' -count=1 -v -timeout=150s
```

Add `LIAISON_TEST_CODEX_INPUT=1` to exercise a real plan-mode choice and answer.
The successful run also reopened the same thread after restarting only the
owned test app-server. Alternatively add `LIAISON_TEST_CODEX_APPROVAL=accept`
or `LIAISON_TEST_CODEX_APPROVAL=decline` to exercise native command approval.
These modes are mutually exclusive with input/write modes. The approval test
accepts only an exact marker-creation command in the temporary working directory;
unexpected or repeated requests fail closed. It asserts that native approval
actually occurred; prompting a harmless no-op alone did not reliably trigger it.
Owned test threads are archived in cleanup where the native server is available.

Full repository `go test -race ./...`, `go build ./...`, and `go vet ./...` passed.
The race build emitted an existing macOS SDK deprecation warning from a dependency.

This change adds opt-in tests and measurements only; it does not change database
schema, retention, production settings, or model configuration.
